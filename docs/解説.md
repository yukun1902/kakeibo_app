## 1. 全体のしくみ

このアプリは、3つの部品でできています。

```
 ┌──────────────┐   リクエスト    ┌──────────────┐     SQL      ┌──────────────┐
 │   ブラウザ    │ ─────────────▶ │  Go サーバー  │ ──────────▶ │  PostgreSQL  │
 │  （画面）     │                │  （main.go）  │              │（データベース）│
 │ HTML/CSS/JS  │ ◀───────────── │              │ ◀────────── │              │
 └──────────────┘   JSON で返事   └──────────────┘    結果      └──────────────┘
```

| 部品 | 役割 | たとえると |
|---|---|---|
| ブラウザ（画面） | 見た目を表示し、ボタンが押されたらサーバーにお願いを送る | お店の客席・メニュー |
| Go サーバー | お願いを受け取り、チェックして、データベースを読み書きする | 店員さん |
| PostgreSQL | データをずっと保存しておく | 倉庫 |

画面は、データベースに直接さわれません。必ず Go サーバーを通します。
こうすることで「ログインしていない人には見せない」「おかしな値は保存しない」といったチェックを、サーバー側で必ず行えます。

### REST API とは

画面とサーバーがやりとりするときの「お願いの書き方の決まり」です。
「どのデータに（URL）」「何をしたいか（メソッド）」を組み合わせてお願いします。

| メソッド | 意味 | 例 |
|---|---|---|
| GET | 取得する | `GET /api/expenses` … 支出の一覧をちょうだい |
| POST | 新しく作る | `POST /api/expenses` … 支出を追加して |
| PUT | 書き換える | `PUT /api/expenses/3` … 3番の支出を書き換えて |
| DELETE | 消す | `DELETE /api/expenses/3` … 3番の支出を消して |

サーバーは、結果を **JSON**（データを文字で表す書き方）と **ステータスコード**（結果を表す番号）で返します。

```json
{ "id": 3, "category_id": 1, "amount": 1200, "date": "2026-10-14", "memo": "スーパー" }
```

| ステータスコード | 意味 |
|---|---|
| 200 / 201 / 204 | 成功（201 = 作れた、204 = 成功したけど返す中身はない） |
| 400 | 送られてきた内容がおかしい（金額が空、日付の形が違う など） |
| 401 | ログインが必要 |
| 404 | 見つからない |
| 409 | 他のデータとぶつかる（同じメールアドレスが登録済み など） |
| 500 | サーバー側で予想外のエラー |

## 3. 1つのリクエストを最初から最後まで追ってみる

「支出を追加する」ときに何が起きているかを、順番に追いかけます。

### ① 画面：保存ボタンが押される（app.js）

入力画面で金額とメモを入れて「保存する」を押すと、`viewAddInput` の中の処理が動きます。

```js
await Api.createExpense({ ...data, category_id: cat.id });
```

`data` には、入力された日付・金額・メモが入っています。

### ② 画面：サーバーにお願いを送る（api.js）

`Api.createExpense` は、`request` という関数を使ってサーバーにお願いを送ります。

```js
createExpense: ({ category_id, amount, date, memo }) =>
  request('POST', '/expenses', { category_id, amount, date, memo }),
```

`request` の中では `fetch`（ブラウザに最初からある機能）を使って、次のようなお願いを送っています。

```
POST /api/expenses
Authorization: Bearer eyJhbGciOi...（ログインのときにもらった JWT）
Content-Type: application/json

{"category_id": 1, "amount": 1200, "date": "2026-10-14", "memo": "スーパー"}
```

### ③ サーバー：どの関数で処理するか決める（main.go の main）

```go
http.HandleFunc("POST /api/expenses", requireAuth(createExpense))
```

「POST で /api/expenses に来たら、`requireAuth` を通してから `createExpense` を呼ぶ」という登録です。

### ④ サーバー：ログインしているか確かめる（requireAuth）

`Authorization` ヘッダーの JWT を取り出して、本物か・期限が切れていないかを確かめます。

- ダメなら → `401 ログインが必要です` を返して終わり
- OK なら → JWT から「会員ID」を取り出して、`createExpense` を呼ぶ

### ⑤ サーバー：中身をチェックする（createExpense → readExpenseInput）

```go
if input.Amount < 1 || input.Amount > 999999999 {
    writeError(w, http.StatusBadRequest, "amount は1〜999999999の整数で指定してください")
    return input, false
}
```

金額が0円、日付の形が違う、などの場合は `400` を返して終わります。

### ⑥ サーバー：データベースに保存する（createExpense）

```go
db.QueryRow(
    "INSERT INTO expenses (category_id, amount, date, memo, user_id) VALUES ($1, $2, $3, $4, $5) RETURNING ...",
    input.CategoryID, input.Amount, input.Date, input.Memo, currentUserID(r),
)
```

- `$1`〜`$5` の場所に、後ろの値が順番に入ります（[なぜ `$1` を使うのか](#sql-の-1-を使う理由とても大事)）
- `user_id` には、④で取り出した「ログイン中の会員ID」を入れます
- `RETURNING` で、保存した行（自動で振られた `id` など）をそのまま返してもらいます

### ⑦ サーバー：結果を返す

```go
writeJSON(w, http.StatusCreated, e)
```

`201 Created` と、保存した支出の JSON を返します。

### ⑧ 画面：結果を受け取って表示を変える

`await Api.createExpense(...)` が終わると、「保存しました」と表示して一覧画面に移ります。
一覧画面は `Api.listExpenses()` で最新の一覧をもらい直して表示します。

> **ポイント：** 他の API も、ほぼ同じ流れです。1つ追いかけられれば、全部読めます。

## 4. Go（サーバー側）の読み方

### ハンドラ関数の形

API の処理をする関数は、すべてこの形です。

```go
func getCategories(w http.ResponseWriter, r *http.Request) {
    // r … 届いたお願い（URL、ヘッダー、本文）
    // w … 返事を書き込む場所
}
```

### 中身はいつも同じ4ステップ

```go
func createCategory(w http.ResponseWriter, r *http.Request) {
    // 1. リクエストから値を取り出す ＋ 2. チェックする
    name, ok := readCategoryName(w, r, 0)
    if !ok {
        return // ダメなときはエラーを返し済みなので、ここで終わり
    }

    // 3. SQL を実行する
    var c Category
    err := db.QueryRow("INSERT INTO categories (name) VALUES ($1) RETURNING id, name", name).Scan(&c.ID, &c.Name)
    if err != nil {
        writeError(w, http.StatusInternalServerError, "カテゴリーの追加に失敗しました")
        return
    }

    // 4. 結果を JSON で返す
    writeJSON(w, http.StatusCreated, c)
}
```

### エラーの書き方

Go では、失敗するかもしれない処理は「結果」と「エラー」の2つを返します。
`if err != nil { ... }` で「エラーがあったら」を毎回確かめるのが Go の書き方です。

```go
id, err := strconv.Atoi("12")   // 文字 "12" を数値 12 に変換
if err != nil {
    // 変換できなかった（"abc" など）ときの処理
}
```

### 構造体と JSON

```go
type Category struct {
    ID   int    `json:"id"`
    Name string `json:"name"`
}
```

`` `json:"id"` `` は「JSON にするときは `id` という名前にする」という目印です。
`writeJSON` に渡すと `{"id": 1, "name": "食費"}` になります。
逆に `readJSON` では、届いた JSON の `"name"` の値が `Name` に入ります。

### SQL の書き方：1行と複数行

| 場面 | 使う関数 | 例 |
|---|---|---|
| 1行だけ欲しい | `db.QueryRow(...).Scan(...)` | ID を指定して1件取得、INSERT ... RETURNING |
| 複数行欲しい | `db.Query(...)` → `for rows.Next()` → `rows.Scan(...)` | 一覧の取得 |
| 結果の行はいらない | `db.Exec(...)` | DELETE |

`Scan` は、SELECT した列の値を変数に入れます。**列の順番と Scan の引数の順番をそろえる**のがポイントです。

### SQL の `$1` を使う理由（とても大事）

```go
// ✕ ダメな書き方（文字をつなげて SQL を作る）
db.Query("SELECT * FROM users WHERE email = '" + email + "'")

// ○ よい書き方（$1 の場所に値を入れてもらう）
db.Query("SELECT * FROM users WHERE email = $1", email)
```

ダメな書き方だと、`email` に `' OR '1'='1` のような文字を入れられたとき、SQL の意味が変わって全員分のデータが取れてしまいます（**SQL インジェクション**）。
`$1` を使えば、値はただの「データ」として扱われるので安全です。

### PostgreSQL のエラーを見分ける

```go
if hasPQCode(err, "23503") { ... }  // 外部キー違反（存在しないカテゴリーID など）
if hasPQCode(err, "23505") { ... }  // 一意制約違反（同じメールアドレスが登録済み）
```

データベースが「それはできません」と言ってきたときに、理由に合ったメッセージとステータスコードを返すために使っています。

### ミドルウェア（門番）

`requireAuth` と `allowCORS` は、本来の処理の手前に立つ「門番」です。

```
リクエスト → allowCORS → requireAuth → getExpenses
              （別の場所     （ログイン
               からでもOK）   してる？）
```

`requireAuth(getExpenses)` のように包むだけで、ログインの確認を付けられます。
各 API に同じチェックを何度も書かなくて済みます。

## 5. データベース

### テーブルの関係

```
users（会員）           expenses（支出）            categories（カテゴリー）
┌────────────────┐     ┌──────────────────┐       ┌──────────────┐
│ id         PK  │◀──┐ │ id           PK  │   ┌──▶│ id       PK  │
│ email   UNIQUE │   └─│ user_id      FK  │   │   │ name         │
│ password_hash  │     │ category_id  FK  │───┘   └──────────────┘
│ created_at     │     │ amount           │
└────────────────┘     │ date             │
                       │ memo             │
                       │ created_at       │
                       └──────────────────┘
```

- **PK（主キー）** … その行を見分けるための番号。`SERIAL` なので自動で 1, 2, 3 … と振られる
- **FK（外部キー）** … 別のテーブルの行を指す番号。存在しない番号は入れられない
- **UNIQUE** … 同じ値は2つ入れられない（同じメールアドレスで2回登録できない）

### 会員ごとにデータを分けるしくみ

`expenses` には `user_id`（誰の支出か）があります。
支出を読み書きする SQL には、必ず `user_id = ログイン中の会員ID` の条件を付けています。

```sql
SELECT ... FROM expenses WHERE id = $1 AND user_id = $2
```

だから、他の人の支出の ID を指定しても「見つかりません（404）」になります。

## 6. ログインのしくみ（ハッシュ化と JWT）

### パスワードのハッシュ化

パスワードは**そのまま保存しません**。bcrypt という方法で、元に戻せない文字列に変換（ハッシュ化）して保存します。

```
"password123"  ──bcrypt──▶  "$2a$10$Xk3vQ9...（60文字）"
```

- データベースの中身が漏れても、元のパスワードはわからない
- ログインのときは、送られてきたパスワードを同じ方法で変換して、保存してあるものと比べる
- bcrypt はわざと計算を遅くしていて、総当たりで破られにくい

### JWT（ログインの証明書）

ログインに成功すると、サーバーは **JWT** を渡します。

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxIiwiZXhwIjoxNzkyMDc1NTk0fQ . uSdGiRcpyt_lYYcF...
└──── 種類 ────┘   └──────────── 中身 ────────────┘   └──── 署名 ────┘
                    {"sub":"1","exp":1792075594}
                    （会員ID 1 番、この時刻まで有効）
```

- **中身** には「誰か（会員ID）」と「いつまで有効か」が書いてある
- **署名** は、サーバーだけが知っている鍵（`.env` の `JWT_SECRET`）で作ったもの
- 中身を書き換えると署名が合わなくなるので、偽物はすぐにわかる

### ログインの流れ

```
【ログイン】
 画面 ── POST /api/login {email, password} ──▶ サーバー
                                              ├ users からメールアドレスで探す
                                              ├ パスワードとハッシュを照合（bcrypt）
                                              └ OK なら JWT を作る
 画面 ◀──────────── {"token": "eyJ..."} ────── サーバー
   └ JWT をブラウザ（localStorage）に保存

【その後のお願い】
 画面 ── GET /api/expenses ──────────────────▶ サーバー
         Authorization: Bearer eyJ...          ├ requireAuth が JWT を確認
                                              ├ 会員ID を取り出す
                                              └ その会員の支出だけ返す
```

### 安全のための工夫

| 工夫 | 理由 |
|---|---|
| ログイン失敗のメッセージを「メールアドレスまたはパスワードが違います」の1つにしている | どちらが違うかを教えると、登録済みのメールアドレスを調べられてしまう |
| 未登録のメールアドレスでも、パスワードの照合と同じだけ時間をかける（`dummyHash`） | 返事の速さの違いから、登録済みかどうかを推測されないため |
| JWT の有効期限は24時間 | 盗まれても、いつまでも使われないようにするため |
| HS256 以外の方式のトークンは受け付けない | 署名なしの偽トークンを通さないため |
| 鍵（JWT_SECRET）はコードに書かず `.env` に置き、git に入れない | 鍵が漏れると、誰でも偽の JWT を作れてしまうため |

## 7. 画面（JavaScript）の読み方

### シングルページアプリ（SPA）

HTML は `index.html` の1つだけです。画面を移るときにページを読み込み直さず、
JavaScript で `<div id="app">` の中身を書き換えて、別の画面に見せています。

どの画面を出すかは URL の `#` 以降で決めます。

| URL | 画面 |
|---|---|
| `#/login` | ログイン |
| `#/home` | ホーム |
| `#/list` | 支出一覧 |
| `#/expenses/3` | 3番の支出の詳細 |

`#` 以降が変わると `render()` が呼ばれ、合う画面が表示されます。

### 1つの画面の作り方

画面ごとに `viewXxx()` という関数があり、「画面の設計図」を返します。

```js
async function viewList() {
  const list = await Api.listExpenses(...);   // ① API からデータをもらう
  return {                                     // ② 設計図を返す
    header: topbar({ title: '支出一覧' }),     //    上のバー
    body: `<div>…${list.map(...)}…</div>`,     //    画面の中身（HTML の文字列）
    nav: 'list',                               //    下のナビで光らせるタブ
    actions: {                                 //    ボタンを押したときの処理
      'clear-filter': () => { state.filter = null; render(); },
    },
  };
}
```

`render()` がこの設計図を受け取って、`#app` に表示します。

### ボタンを押したときの処理

ボタンに `data-action="名前"` を付けておくと、押されたときに `actions['名前']` が呼ばれます。

```html
<button data-action="clear-filter">解除</button>
```

### 状態（state）

「表示している月」「選んでいる日」など、画面を移っても覚えておきたい値は `state` に入れています。
値を変えたら `render()` を呼んで描き直す、というのが基本の動きです。

```js
'next-month': () => { state.month = addMonths(state.month, 1); render(); },
```

### async / await

API の返事はすぐには来ないので、「返事が来るまで待つ」書き方をしています。

```js
const list = await Api.listExpenses();  // 返事が来るまで待ってから、次の行に進む
```

`await` を使う関数には、頭に `async` を付けます。

### ログイン状態の管理（api.js）

- ログインでもらった JWT を `localStorage`（ブラウザの保存場所）に保存
- `request()` で毎回 `Authorization: Bearer <JWT>` を付けて送る
- サーバーが `401` を返したら（期限切れなど）、JWT を消してログイン画面に戻す
- ログアウトは、保存している JWT を消すだけ

## 8. 自分で動かして試す

### サーバーを起動する

```
cd kakeibo_app
go run .
```

`サーバーを起動しました: http://localhost:8080` と出たら、ブラウザで開きます。
止めるときは、ターミナルで `Ctrl + C` を押します。

### curl で API を直接呼んでみる

画面を使わずに、API だけを試せます（Git Bash で実行）。

```bash
# 会員登録
curl -X POST -H "Content-Type: application/json" \
  -d '{"email":"taro@example.com","password":"password123"}' \
  http://localhost:8080/api/register

# ログイン（返ってきた token をコピーする）
curl -X POST -H "Content-Type: application/json" \
  -d '{"email":"taro@example.com","password":"password123"}' \
  http://localhost:8080/api/login

# ログインせずに一覧を取る → 401 になる
curl http://localhost:8080/api/expenses

# token を付けて一覧を取る
curl -H "Authorization: Bearer ここにtoken" http://localhost:8080/api/expenses

# 支出を追加する
curl -X POST -H "Content-Type: application/json" -H "Authorization: Bearer ここにtoken" \
  -d '{"category_id":1,"amount":1200,"date":"2026-10-14","memo":"スーパー"}' \
  http://localhost:8080/api/expenses
```

### ブラウザの開発者ツールで見る

画面で操作しながら、ブラウザの開発者ツール（F12）の「ネットワーク」タブを開くと、
画面がサーバーにどんなお願いを送り、どんな返事が来たかを1つずつ見られます。
この資料の「3. 1つのリクエストを追ってみる」を、実際の画面で確かめてみてください。

### データベースの中身を見る

```bash
psql -U postgres -d kakeibo_app
```

## 9. 用語集

| 用語 | 意味 |
|---|---|
| API | プログラム同士がやりとりするための窓口 |
| REST API | URL とメソッド（GET/POST/PUT/DELETE）でお願いを表す API の決まり |
| リクエスト / レスポンス | お願い / 返事 |
| JSON | `{"id": 1, "name": "食費"}` のように、データを文字で表す書き方 |
| ステータスコード | 結果を表す番号（200 = 成功、404 = 見つからない など） |
| エンドポイント | API の1つ1つの窓口（`POST /api/expenses` など） |
| ハンドラ | 1つのエンドポイントの処理をする関数 |
| ルーティング | 「この URL ならこの関数」と結びつけること |
| ミドルウェア | 本来の処理の手前で共通のチェックをする関数（門番） |
| SQL | データベースに命令する言葉（SELECT = 読む、INSERT = 追加、UPDATE = 更新、DELETE = 削除） |
| 主キー（PK） | 行を見分けるための番号 |
| 外部キー（FK） | 別のテーブルの行を指す番号。存在しない番号は入れられない |
| SQL インジェクション | 入力に SQL を混ぜて、勝手な命令を実行させる攻撃。`$1` を使えば防げる |
| ハッシュ化 | 元に戻せない文字列に変換すること。パスワードの保存に使う |
| bcrypt | パスワードのハッシュ化によく使われる方法 |
| JWT | 署名付きの「ログインの証明書」。中身を書き換えると偽物だとわかる |
| トークン | 証明書や合言葉のような文字列。ここでは JWT のこと |
| 環境変数 | プログラムの外に置く設定（`.env` に書いた DATABASE_URL など） |
| CORS | 別の場所の画面からの API 呼び出しを、サーバーが許可するしくみ |
| SPA | HTML を読み込み直さず、JavaScript で画面を切り替えるアプリ |
| fetch | ブラウザからサーバーにリクエストを送る JavaScript の機能 |
| async / await | 時間のかかる処理の終わりを待つための JavaScript の書き方 |
| localStorage | ブラウザの中にデータを保存しておける場所 |
